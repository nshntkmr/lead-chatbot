# CLAUDE.md — ACO Data Assistant

Login-protected chat app where actuaries / finance leaders ask Claude questions about CMS ACO workbook extracts (LEAD and MSSP, one row per TIN). FastAPI + SSE streaming, SQLite (users, chats, usage ledger), DuckDB read-only warehouse built from `data/*.csv|xlsx`, Anthropic SDK tool-use loop. Plain HTML/JS front end in `static/`. **Read `docs/PROJECT_CONTEXT.md` first** — the full handover: end users, every file, the two datasets, the column dictionary, verified math, history of fixes, open items. `README.md` is the operator guide; `TESTING.md` holds golden answers computed from the raw CSVs.

## Map

| Path | Role |
|---|---|
| `app/main.py` | routes: login/lockout, chats CRUD, `/api/usage`, streaming `/api/chat`; module-level dict is `runtime` (per-chat dict is `state`) |
| `app/agent.py` | TOOLS, SYSTEM_TEMPLATE rules, `make_client()` (Anthropic or Microsoft Foundry), tool loop, history compaction, usage events |
| `app/portfolio.py` | deterministic portfolio math (`LeadSpec`, `MsspSpec`, `PortfolioCalc.metrics/suggest`, `compare_programs`) |
| `app/data.py` | warehouse build, program detection from file name, dictionary linking, column notes, `search_columns`, safe `query` |
| `app/dictionary.py` | column-dictionary parsing + exact/cell/pattern linking |
| `app/store.py`, `app/pricing.py`, `app/config.py` | SQLite schema, rate card, `.env` settings (`APP_VERSION` lives here) |
| `data/context.md`, `data/context-lead.md`, `data/context-mssp.md` | domain notes injected into the system prompt — the main lever on answer quality |
| `data/column_notes-lead.csv` | generated by `scripts/make_lead_notes.py`; edit the script, not the CSV |
| `scripts/manage_users.py`, `scripts/rebuild_data.py` | users; force warehouse rebuild |
| `evals/` | `TESTING.md` automated: `cases.py` (chat cases; every expected figure has a sign and says which metric it is), `grade.py` (deterministic pass + model judge, with a self-test of the judge), `offline.py` / `offline_infra.py` (no model calls: portfolio goldens, guard rails, turn lock, rebuild manifest, deadlines, rendered chart values), `run.py` |

## Rules

- Never modify, reformat or re-save the source data files in `data/` (`*_200plus.csv`, the dictionary). They are read-only inputs and are git-ignored.
- Never put API keys or other secrets in code, docs or chat. They live only in `.env` (`.env.example` is the template). `.env`, `app.db`, `.secret_key`, `data/warehouse.duckdb` stay out of git.
- Bump `APP_VERSION` in `app/config.py` on every change that affects answers; it is logged at startup (`Ready (app version …)`) and shown in the usage panel, so stale deployments can be spotted.
- Portfolio math must reproduce the workbook's own per-TIN results to within rounding. Identities to keep: Total benchmark = PBPM × person-years × 12; MLR = Σexpense ÷ Σbenchmark (never an average); LEAD cohort benchmarks must be scaled by (after discount & quality ÷ before discount) so cohorts sum to the total; LEAD "loss = 100% of benchmark" is a scenario, not a cap; MSSP ENHANCED caps (20% / 15%) are reported but not applied by the workbook.
- The column dictionary is the authoritative definition source. Columns like `ESRD`, `High Needs (HN) - 2025` are worksheet label cells (constant in every row), not data — see `column_notes-lead.csv`.
- SQL from the model is single-`SELECT` only, run against a read-only DuckDB with external access disabled and a 30 s timeout, limited to the chat's own dataset, with results capped by rows and by size (`MAX_RESULT_CHARS_*`). Keep it that way.
- Enforce behaviour in code or tool output before adding a prompt rule: tool results use the words users should read (`room_under_target_usd`, not headroom/slack), and limits are applied by the tool, not requested in the prompt.
- Data CSVs are loaded by DuckDB's own reader (`_load_csv`), not pandas, so memory stays flat at any row count. One row per TIN is assumed throughout: files of one program with the same header load as one table, and `build_spec` refuses (with a message the user sees) a program with two headline tables or a repeated TIN rather than computing on part of the data.
- Every query a tool makes goes through `Warehouse.execute` (deadline + `MAX_CONCURRENT_QUERIES` slots); never call `wh.con` from a tool. Every tool result passes `within_budget` before it reaches the model.
- One question at a time per chat: `store.acquire_turn` before the transcript is read, `save_conversation(token=…)` to write it. Do not reintroduce in-process state for this — it must hold across workers. The same goes for the login lockout (`store.begin_login_attempt`, keyed by `main.client_ip`, which trusts `X-Forwarded-For` only for `TRUSTED_PROXY_HOPS` proxies).
- Percentages in charts are percentage values (87.35), never fractions; the chart block carries `percent_scale`.
- The warehouse rebuilds when the source manifest (names, sizes, modified times) changes, not only when a file is newer.
- Keep the front end CDN-free (vendored marked / DOMPurify / Chart.js).

## Running and checking

```
.venv\Scripts\python -m uvicorn app.main:app --port 8000      # or start.bat
.venv\Scripts\python -m scripts.manage_users add <user> --admin
.venv\Scripts\python -m scripts.rebuild_data
.venv\Scripts\python -m evals.run --offline                 # deterministic checks, free, under a minute
.venv\Scripts\python -m evals.run                           # + all chat cases against the model (~$1.60, ~4 min)
```

After any change to `portfolio.py`, `agent.py`, `data.py`, `main.py`, `store.py` or `data/context*.md`, run `python -m evals.run` (at least `--offline`); a failing case names the check and the report in `evals/results/` holds the full answer. A figure passes only when it is shown with the right sign and the judge agrees it is stated for that metric; `--no-judge` is for a quick look and proves nothing about correctness. Read the "judge observations" at the end of a run: they do not fail a case but are where prose slips show up. Add a case to `evals/cases.py` for every new behaviour or bug fix, and update expected values only if the raw CSV says so. `TESTING.md` remains the manual script for the UI checks (Part C).
